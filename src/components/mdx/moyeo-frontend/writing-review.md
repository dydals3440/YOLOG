# 편집 검토

2026-10-11 최종 본문 기준. 제목·슬러그를 유지하고 발행일은 2026-10-11로 둔다.

## 이전 글이 끊겨 읽힌 이유

참고한 [서버 모니터링 분석 가이드](https://kciter.so/posts/server-monitoring-analysis-guide/)는 증상을 보고 원인을 좁히는 한 가지 순서로 독자를 이끈다. 도식 앞에는 무엇을 볼지, 뒤에는 무엇을 판단할지 적는다. 글의 길이보다 다음 문단이 앞의 질문에 답하는지가 중요했다.

모여 글에는 요청을 반영하며 덧붙인 문법 설명과 예외 조건이 많았다. 검색 조건을 이미 보여 줬는데 trim·undefined·연산자를 다시 풀이하고, 문제가 없는 코드까지 Before로 제시했다. 코드·설명·보충 설명이 같은 결론을 반복하면서 제품의 상황이 흐려졌다. 이것은 문장으로 AI 작성 여부를 판정한 것이 아니라, 읽기 어려워진 편집상의 원인을 정리한 것이다.

kciter.so는 공개 글 58개의 제목·도입·구조·맺음을 조사하고, Thoughts 10편과 관련 기술 글을 중심으로 정독했다. 모든 58편의 전문을 정독했다는 뜻은 아니다. 글쓴이의 표현이나 경험을 복사하지 않고 전개의 원칙을 참고했다.

## 반영한 편집

- 페이지 → 상태 → 목록 → 계약·정책으로 변경할 위치를 좁힌다. 이후 영상 첨부 → 편집 → 예약 → 여러 탭에서 결과 확인 → 행동 분석으로 제품 사용 순서를 따른다.
- 검색 사례는 신메뉴 안내의 임시 저장 목록으로 통일한다. URL은 q, 페이지는 query, API는 searchText이며 이름의 연결을 한 번만 설명한다.
- 중복 검색 조건 예제와 trim/??/||의 문법 설명을 삭제했다. select의 비교용 Before도 없애고 실제 무한 목록의 선택 함수 하나로 설명한다.
- 핵심 기준인 튜플 인터페이스, 예측 가능한 입력 Props, 화면 이름 대신 조건을 받는 목록, 페이지의 로딩·오류 경계, 공용 계약과 순수 정책은 남겼다.
- 상세 데이터도 사용하는 곳에서 읽는다는 요구는 실제 PostArticle의 짧은 조회 예제로 보완했다. 라우트 의존성과 재사용 범위도 같은 자리에서 설명한다.
- JSX에는 필요한 화면 순서를 남긴다. Header/Contents/Footer를 임시 변수로 만드는 예제나 의미 없는 추출을 추가하지 않는다.
- 여섯 큰 주제 앞에는 `---`, 같은 주제 안의 논점 전환에는 소제목을 사용한다. 고정 행의 변경, URL 검증과 저장소 교체, 상세 조회, 공유 계약을 구분하고 관련 설명은 해당 예제 가까이에 둔다.
- 코드 예제는 설명하려는 판단만 남긴다. 금액 변환 예제의 부가 속성과 상세 조회의 불필요한 ID 별칭을 덜어냈다. 고정 행 예제는 PostInfoCard의 Content·Empty와 같은 파일의 PostInfoRow·Message로 구성한다. 화면 상태의 네임스페이스와 반복 스타일의 지역 컴포넌트를 구분하며, 게시 상태의 배지 값은 별도 줄에서 강조한다.
- 외부 각주는 21개에서 7개로 줄였다. Query select·nuqs·oRPC·해싱·탭 통신의 공식 자료와 측정 조건을 남겼다.
- 추상화, Context API, TanStack Router, Suspense, Facade, 의존성 주입, SSE는 기존 블로그 글 7편을 해당 문맥에 연결했다.
- 마무리는 다음 요구사항에서 얻은 이점, 선택에 따라 남은 책임, AI와 경험에 대한 개인적인 생각의 세 문단으로 정리했다. 일반적인 직업론과 미래의 성공에 대한 긴 맺음말은 덜었다.

## 이번 전체 편집에서 조정한 부분

- 큰 제목은 컴포넌트·상태·조회·계약과 정책·게시 과정·회고의 여섯 주제로 정했다. 소제목은 실제로 고민한 문제를, 코드 제목은 비교할 차이를 설명한다.
- Before/After의 결과를 맞췄다. 고정 행은 양쪽 모두 상태 배지를 표시하며, 목록은 양쪽 모두 초안을 조회한다. 입력 예제도 같은 안내와 접근성 속성을 사용한다.
- 고정 행의 배치 비교와 상세 화면의 네임스페이스를 나눴다. Content는 한 번만 보여 주고, 다음 소제목에서 Empty와 지역 스타일 컴포넌트를 설명한다.
- 목록의 조건 → 실제 조회와 select → 로딩·오류 경계 → 상세 조회 → 사전 조회로 순서를 바꿨다. SSR 설명은 사전 조회 뒤에 이어지는 한 문단으로 줄였다.
- `select`는 실제 무한 목록의 페이지를 펼치는 용도로 유지한다. 한 사용처의 단순 flatMap도 충분하다는 점을 남기고 불필요한 Before를 만들지 않았다.
- `12_900`, `1_024`, `60_000`처럼 코드의 수치 표기를 맞추고, 긴 표현은 줄바꿈했다. 날짜 문자열과 화면에 표시하는 금액은 바꾸지 않았다.
- 코드 제목 변경에 맞춰 예제를 추출하는 테스트의 제목만 갱신했다. 행동 검증은 그대로 유지한다.
- 사용자의 후속 요청으로 서론 다섯 문단은 이번 편집 전 내용으로 복원했다. 입력 뒤의 일관성 인용문도 유지한다.
- 예제 앞의 구성 요소 소개는 비교할 지점으로 바꿨다. QueryBoundary·formatCount·공유 타입처럼 필요한 정의는 짧은 코드 주석으로 옮기고, 타입이나 컴포넌트의 뜻을 본문에서 반복하지 않는다.

## API 계약과 화면 정책 절의 후속 편집

- 내부 타입 공유와 외부 HTTP API·MCP 확장이라는 요구를 먼저 밝히고, REST+OpenAPI+Orval·tRPC·oRPC를 한 표에서 비교했다. Orval 설정 예제는 하나만 유지하고 공통 장점을 반복하는 문단은 합쳤다.
- 계약의 Before/After는 중복 정의와 공유 정의를 비교한다. PostArticle은 post.text를 읽기만 하던 코드 대신 본문을 표시한다. SSE는 게시물 변경 이벤트를 처리 함수에 전달하는 동작으로 바꿨다.
- 조회 → 변경 신호 → 누락에 대비한 재조회 정책 순서로 연결했다. 정책과 Given/When/Then 테스트를 같은 소절에 두고, 폴더·lint에 관한 별도 이야기는 덜었다.
- REST와 oRPC를 배타적인 방식으로 설명하지 않는다. tRPC의 SSE, Orval의 MCP 생성도 함께 인정하며 oRPC가 모여의 계약 관리 방식에 맞았다는 이유를 남겼다. 실제 oRPC beta 문법과 tRPC OpenAPI alpha 상태는 각주에서 구분한다.
- 서론·다른 기술 사례·맺음말·이미지는 수정하지 않았다. 새로운 Canvas 없이 비교표와 코드 강조로 전달한다.

## 시각 자료

본문에서 쓰는 WebP 3개를 유지한다. 실제 게시물 화면은 화면 순서를, 편집 보호 그림은 응답 순서를 보여 준다. 커버는 도입 이미지다. 사용하지 않는 전용 WebP는 없다.

리더 탭 도식은 시간이 흐르며 연결 주체가 달라지므로 유지한다. ‘연결 회전’은 ‘연결 교체’로 바꾸고 캡션의 반복 설명을 줄였다. 브라우저 API를 직접 실행하는 시뮬레이터가 아니라 동작 설명이다. 업로드 수치와 시간대는 표로 비교한다.

## 권한·시간대 보강 — 2026-10-11

- API 계약 다음에 채널 연결 사례를 추가했다. 역할만 확인하는 Before와 `actions.connectChannel`을 구독하는 After를 비교하고, ABAC·Entitlement·Quota의 기준을 구분했다. 실제 `ActionButton`의 안내와 `PlanGateButton`의 요금제 연결은 구분해 설명한다.
- DB가 보관하는 사실, 서버 `AccessControl`의 최종 판단, 화면의 안내 책임을 나눴다. 트랜잭션 내 재검사와 잠금은 실제 채널 연결 adapter에서 확인했다. SSR에서 준비한 Query 캐시를 이어받고 변경 후 같은 Query를 구독하는 UI와 라우트 context의 차이도 명시했다.
- 기존 DST 사례에 지역 예약 의도와 확정 시점의 저장 차이를 추가했다. DB schema의 `timestamptz(3)`·지역 필드, UTC 연결 설정과 서버 시간대 해석을 대조했다.
- 예약 절 뒤에 SSR 표시 절을 추가했다. 실제 `useAuthContext`, `useNowAt`, `formatUpcomingInstant`를 사용하고, `useDeviceTimeZone`과 `useLiveClock`의 hydration 이후 동작을 설명했다. 캘린더·성과 집계·결제 계산의 시간대 기준과 캘린더 Query Key도 제품 코드와 문서에 맞췄다.
- 권한·quota 및 시간대 fallback·시계 hydration의 기존 제품 테스트를 읽어 설명과 대조했다. 제품 테스트를 새로 작성하거나 실행한 것은 아니다. ABAC 내부 글과 PostgreSQL·TanStack Start 공식 문서 두 개를 연결했다.
- 추가한 컴포넌트 예제 4개를 실제 모여 타입으로 검사해 예제·의존 파일 진단 모두 0개였다. 본문 문법을 포함한 unit test 24개 통과, 97페이지 빌드 통과.
- 편집 전 파일과 비교해 서론·메타데이터·마무리가 동일함을 확인했다. 생성 HTML에서 새 소제목, 각주, ABAC 내부 링크, 하이라이트 지시문 비노출을 검사했다.
- Chrome 데스크톱과 390×844 모바일에서 새 절의 제목·예제·강조를 확인했다. 시간대 함수 선언과 인자는 좁은 화면에서도 핵심 입력이 보이도록 줄바꿈했다. 모바일 문서 너비는 379px로 가로 넘침이 없었으며, 임시 viewport는 해제했다. 기존 이미지와 애니메이션은 유지했다.


## 사용 흐름에 따른 전체 재구성 — 2026-10-11

- 서론·제목·날짜·메타데이터는 편집 전 원문과 동일하게 유지했다. 본문은 페이지 → 상태 → 조회 → 계약과 권한 → 업로드와 편집 → 예약과 SSR → 여러 탭 → 분석 → 마무리의 아홉 장으로 나누었다. 이후 요청에 따라 `참고자료`를 별도 마지막 섹션으로 추가했다.
- 게시물의 검색·편집·예약·결과 확인으로 예제를 연결했다. 가격 입력은 공개 페이지의 별도 사례임을 밝혔고, 중복 카드 구현을 덜었다. `ExpandedPostView`로 실제 두 보기와 누락 검사용 세 보기의 타입을 구분했다.
- 목록의 `select`는 실제 무한 조회의 페이지를 목록으로 읽는 사례로 비교했다. 단순한 컴포넌트 가공도 가능한 선택임을 남기고 캐시 원본, 서버 검색, 화면 가공을 구분했다. SSE 계약과 사용 예제는 탭 동기화 장으로 모았다.
- 권한은 DB의 사실·서버의 판단·클라이언트의 안내로 나누었다. 시간대 비교는 같은 날짜 표시 방식으로 맞추고, 서버와 첫 화면의 기준 시각 문제는 별도 소절로 구분했다.
- 마무리는 누군가의 불편을 해결하는 과정의 즐거움에서 출발한다. 사용자의 반응을 듣고 다시 시도하기 위한 변경 용이성, 제품과 사업을 넓게 보는 시야, 깊은 기술 경험의 필요성을 연결했다. 해결 방법이 반드시 개발일 필요는 없다는 최신 요청도 반영했다.
- 단위 테스트 24개, 사이트 타입 검사, lint·format 검사, 97페이지 빌드, 사이트 검증 20개가 통과했다. 실제 제품 의존 타입으로 검사한 핵심 예제 13개의 예제 자체 진단은 0개이며, 제품 의존 파일의 기존 진단 11개는 별도로 구분했다. 제품 저장소는 수정하지 않았다.
- Chrome에서 데스크톱 목차와 모바일 Before/After·시간대·마무리를 확인했다. 모바일 전체 가로 넘침은 없었다. 리더 도식은 화면 진입 후 정상 활성화되고 ‘신호 공유’ 선택 시 3단계로 전환되었다. 임시 모바일 viewport는 해제했다. 추가한 참고자료 제목과 번호 목록도 데스크톱에서 확인했다.


## 컨테이너와 DB 연결의 시간대 기준 — 2026-10-11

- 예약 절에 ‘컨테이너부터 화면까지 시간의 기준을 정한다’를 추가했다. 실제 서버 Dockerfile의 `ENV TZ=UTC`, 로컬 Compose의 서버·PostgreSQL UTC 설정, `packages/env`의 UTC literal 검증, `packages/db`의 연결 시작 옵션을 대조했다.
- Docker 환경 변수와 PostgreSQL 세션 설정은 별개임을 설명하고, 네 계층의 책임을 표로 정리했다. UTC 실행·저장 기준과 사용자가 선택한 지역 시간대의 보존·표시를 구분한다.
- `database-session-settings.integration.spec.ts`의 서울 시간대 DB에 대한 세 연결 검사와 `time-zone-runtime-composition.spec.ts`의 세 프로세스 시간대 비교를 읽어 본문에 반영했다. 제품 테스트를 실행한 것으로 표현하지 않는다.
- 이 글의 단위 테스트 24개, 빌드 97페이지, 사이트 검사 20개가 통과했다. 데스크톱에서 새 표의 줄바꿈과 섹션 흐름을 확인했다.
- 마무리에 누군가에게 도움이 되는 즐거움이 꾸준한 사이드 프로젝트로 이어진다는 문장을 반영했다. 서론과 메타데이터는 유지했다.
